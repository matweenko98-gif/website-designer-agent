# Стек по умолчанию: рабочий сайт, а не макет

Применять, когда пользователь не задал технологии и в проекте ещё нет своего стека. Если стек уже есть — сохраняй его. Цель: сайт, которым можно пользоваться сразу и развивать дальше, с рабочей формой заявок и публикацией в интернете.

## Что используем

- **Next.js** (актуальная стабильная версия, App Router) и **TypeScript**
- **Обычный CSS** (глобальные стили и CSS Modules): правила `DESIGN.md` рассчитаны на собственную вёрстку. Tailwind и UI-киты — только по желанию пользователя
- **Supabase** — база заявок, **Telegram Bot API** — уведомления о заявках (`LEADS.md`)
- **Vercel** — публикация
- npm как менеджер пакетов

Next.js быстро меняется. Не полагайся на память: читай документацию той версии, что установлена (`create-next-app` кладёт в проект `AGENTS.md` со ссылкой на неё в `node_modules/next/dist/docs/`), и следуй предупреждениям об устаревших API.

## Где лежит код

Сайт создаётся в подпапке `site/` рядом с этим пакетом — так файлы Next.js (в том числе его собственный `AGENTS.md`) не перезапишут инструкции агента. `PROJECT.md`, `content/` и прочие рабочие файлы остаются в корне.

```bash
npx create-next-app@latest site --ts --app --eslint --no-tailwind --import-alias "@/*" --use-npm --yes
```

`site/` — отдельный git-репозиторий сайта: его публикуют и развивают независимо от пакета агента.

## Свой репозиторий пользователя

Пакет агента скачан или склонирован из чужого репозитория (`website-designer-agent`). Это не репозиторий пользователя: никогда ничего туда не отправляй, не предлагай отправить и не рассказывай пользователю, чей он и почему туда нельзя. Если среда или проверка просит отправить изменения, а под рукой только репозиторий агента — не отправляй, а переходи к созданию своего репозитория по шагам ниже.

Сайт пользователя хранится в **его собственном** репозитории на GitHub — так сайт остаётся у него, и с него Vercel публикует сайт. Создай его, когда дойдёт до сохранения на GitHub или публикации (шаг 6), а если среда требует сохранять раньше — сразу:

- Пользователь вошёл в GitHub CLI (`gh auth status`) — создай сам: `gh repo create <название-сайта> --private --source site --push`. Скажи одной фразой: «Создал для вашего сайта отдельное хранилище на GitHub — оно только ваше»
- Не вошёл — проведи по шагам: открыть [github.com/new](https://github.com/new) → в поле **Repository name** написать название сайта латиницей → выбрать **Private** → ничего больше не отмечать → **Create repository** → прислать ссылку на страницу, которая откроется. Затем подключи `site/` к этому репозиторию и отправь код сам

Объясняй это образом из `TEACHING.md`: GitHub — хранилище с машиной времени, и у сайта должно быть своё.

## Как строить

- Страницы — серверные компоненты со статической отрисовкой: весь текст есть в HTML (это важно и для SEO/GEO). Клиентские компоненты (`"use client"`) — только для интерактивных частей: форма, меню, слайдер. Не делай страницу целиком клиентской
- Шрифты — через `next/font` с подмножеством `cyrillic` для русского текста; изображения — через `next/image` (`IMAGES.md`)
- SEO-слой — средствами Next.js: `metadata` / `generateMetadata`, `app/sitemap.ts`, `app/robots.ts`, `opengraph-image` или файл в `public/`, `public/llms.txt`, JSON-LD тегом `<script type="application/ld+json">` в разметке страницы (`SEO_GEO.md`)
- Серверная часть формы — обработчик `app/api/lead/route.ts` (`LEADS.md`)
- Простая структура: одна страница, если не согласовано больше; без базы данных, CMS и авторизации сверх нужного
- Перед показом: `npm run build` и `npm run lint` проходят без ошибок

## Секреты

- Ключи живут в `site/.env.local` (не попадает в git и в интернет) и в настройках Vercel. В репозитории — только `site/.env.example` с названиями переменных и пустыми значениями
- Серверные ключи — без префикса `NEXT_PUBLIC_`: всё с этим префиксом видно любому посетителю сайта
- Проверь, что `.env*` (кроме `.env.example`) есть в `.gitignore`, до первого коммита
- Пользователь вставляет ключи сам; ты готовишь файл и говоришь, в какую строку что вставить (правило «Простой язык» в `AGENTS.md`)

## Публикация на Vercel

Только по поручению пользователя. Аккаунты и вход делает пользователь; ты ведёшь его по шагам.

1. Сайт собирается локально без ошибок (`npm run build`)
2. Публикация одним из способов:
   - **Через GitHub** (способ по умолчанию: дальше каждое изменение публикуется само). Сначала проверь `gh auth status`. Если пользователь вошёл в GitHub CLI — сделай всё сам: коммит в `site/` и `gh repo create <название> --private --source site --push`. Если `gh` нет или вход не выполнен — проведи по шагам: установка с [cli.github.com](https://cli.github.com), `gh auth login` (GitHub.com → HTTPS → Yes → Login with a web browser). Затем в Vercel — **Add New… → Project → Import** этого репозитория. Ключи удобнее добавить прямо на экране импорта, в **Environment Variables**, до нажатия **Deploy** — тогда повторная публикация не нужна. Дальнейшие правки: коммит и `git push` — Vercel опубликует их сам
   - **Без GitHub, из терминала**: `npx vercel` в папке `site/`, вход в аккаунт по ссылке из терминала, ответы на вопросы по умолчанию; финальная публикация — `npx vercel --prod`
3. Ключи: в проекте Vercel — **Settings → Environment Variables**, те же названия, что в `.env.example`, значения — из `.env.local`. Если ключи добавлены после первой публикации — нужна повторная публикация (**Deployments → Redeploy** или `npx vercel --prod`), иначе сайт их не увидит
4. Проверка: открыть ссылку с телефона, отправить тестовую заявку, убедиться, что она пришла в Telegram и появилась в базе

Бесплатный тариф Vercel (Hobby) по правилам Vercel — для некоммерческого использования. Для сайта действующего бизнеса один раз скажи об этом пользователю: дальше понадобится тариф Pro или другой хостинг. Учебный и тестовый запуск на Hobby — нормально.

Свой домен подключается потом: в Vercel **Settings → Domains**, затем записи у регистратора домена. После этого обнови абсолютные адреса в SEO-слое (`SEO_GEO.md`).
